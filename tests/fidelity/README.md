# Сверка модели с игрой (M0)

Эталоны снимаются из настоящей Factorio 2.0 (base + space-age) модом `factorio-distributed`
и лежат здесь: `<name>.scene.json` (сцена) и `<name>.dump.jsonl` (состояние каждый тик).

- `*.scene.json` здесь — основные сцены (3600 тиков) и `compressed-restart-*` (перезапуск
  сжатой очереди, 900 и 400 тиков);
- `probes/` — пробные сцены (обычно 300–800 тиков): направления, частные случаи, линии лент,
  конкуренция манипуляторов. Списки «совпадает» / «известное расхождение» — в `tests/fidelity.rs`.

Снять заново: поднять сервер (`bench/run-server.ps1`, см. `bench/README.md`) и
`cargo run --release --bin scene_capture -- tests/fidelity/<name>.scene.json [...]`.
Все сцены из командной строки строятся одновременно, каждая на своей поверхности, и пишутся
с общим t = 0. Перед записью `scene_capture` сверяет геометрию модели с числами игры
(`drop_position` / `pickup_position` манипуляторов, `get_line_item_position` лент — операция
мода `scene_info`), проверяет, что у манипуляторов нет бонуса размера руки (бонусы исследований
силы и ручной предел — нули: модель знает только руку прототипа), и останавливается при расхождении.

Числа сущностей модель берёт из выжимки `data.raw` (`data/prototypes-m0.json`, Factorio 2.0.77,
base + space-age + quality + elevated-rails). Пересобрать под другой набор модов:
`factorio --dump-data` с этими модами, затем
`cargo run --release --bin proto_extract -- --in <script-output/data-raw-dump.json> --out data/prototypes-m0.json --source "<версия и моды>"`.

Файлы эталонов хранятся в git как есть (`.gitattributes`: `-text`, концы строк LF); парсер
эталона терпит и CRLF.

## Сцена

```json
{"name": "straight-belt", "ticks": 3600,
 "entities": [{"name": "wooden-chest", "position": [0.5, 0.5], "items": {"iron-plate": 200}},
              {"name": "inserter", "position": [1.5, 0.5], "direction": "west"},
              {"name": "transport-belt", "position": [2.5, 0.5], "direction": "east"}]}
```

Ограничения (мод проверяет их до постройки и отвечает ошибкой):
- `name` — `[a-z0-9_-]+` (нижний регистр, до 100 символов, не `con`/`nul`/`aux`/`prn`/`com1-9`/`lpt1-9`): из него делается имя файла эталона;
- `ticks` — целое от 1 до 100 000;
- сущности — только из белого списка M0: `transport-belt`, `fast-transport-belt`,
  `express-transport-belt`, `turbo-transport-belt`, `wooden-chest`, `iron-chest`, `steel-chest`,
  `inserter`, `fast-inserter`, `long-handed-inserter`; не больше 2000;
- `position` — центр сущности `[x, y]` в тайлах, на середине тайла (x.5), `|x|, |y| <= 64`;
  дамп пишет **настоящую** позицию поставленной сущности (мод проверяет, что она равна входной);
- `direction` — `north` / `east` / `south` / `west` (по умолчанию `north`);
- `pickup` / `drop` — только у манипулятора, необязательно: `[dx, dy]`, смещение точки захвата /
  выгрузки от центра в тайлах (`|d| <= 8`). Работает только с тестовым модом `fd-test-vectors`
  (без него мод отвечает ошибкой «не применился»); мод записывает абсолютную точку «центр + вектор»,
  игра хранит её с усечением к нулю до 1/256 (при положительной координате — вниз, при
  отрицательной — вверх);
- `warmup` (на верхнем уровне сцены, необязательно) — сколько тиков прошло от постройки до
  t = 0; читает только модель (мод поле не использует). Нужно для проб состояния лент сразу после
  постройки (`build-*`): первые до 600 тиков каждая лента — своя линия. Без поля модель считает,
  что прошло `WARMUP_SETTLED` (1024) тиков; съёмщики столько и ждут;
- `items` — только у сундука: `{"имя предмета": число}`, предмет должен существовать, число —
  целое > 0. Мод кладёт предметы в сундук **в порядке имён** (как `BTreeMap` в ядре), поэтому
  порядок слотов задан сценой.

Мод строит каждую сцену на своей поверхности из пула `fd-scene-<n>` (только плитка lab, без
рельефа) и ставит питание: подстанцию с собственным бесконечным источником энергии рядом с
каждым манипулятором, который ещё не покрыт (радиус — `get_supply_area_distance()` прототипа
подстанции), не занимая клетки захвата/выгрузки манипуляторов. Перед записью мод проверяет,
что каждый манипулятор подключён к сети и с энергией, иначе — ошибка.

## Эталон

Одна строка JSON на тик, t = 0 .. ticks включительно (ticks + 1 строк):

```json
{"t": 0,
 "belts": [{"pos": [2.5, 0.5], "lines": [[{"item": "iron-plate", "p": 64}], []]}],
 "inserters": [{"pos": [1.5, 0.5], "held": "iron-plate", "held_count": 1, "hand": [128, 128]}],
 "chests": [{"pos": [0.5, 0.5], "items": {"iron-plate": 199},
             "slots": [["iron-plate", 100], ["iron-plate", 99]]}]}
```

Если сцена запущена с `"ext": true` (`scene_run_all`), в запись манипулятора добавляются
`"pickup": [x, y]` и `"drop": [x, y]` — фактические точки захвата и выгрузки, абсолютные координаты
в 1/256 тайла (`pickup_position` / `drop_position` игры).

Сущности в массивах идут в порядке появления в сцене. `lines[0]` — линия 1, `lines[1]` — линия 2
(`get_transport_line(1/2)`). `hand` — абсолютные координаты `held_stack_position`, в 1/256 тайла.
`slots` — слоты сундука по порядку инвентаря (`[имя, число]` или `null`), хвост пустых слотов
отрезан.

## Что значит «тик 0»

Снимок t = 0 — сундуки только что заполнены, манипуляторы запитаны и прогреты, ни одного
обновления игры с предметами ещё не было. Мод требует не меньше 60 тиков после постройки;
съёмщики (`scene_capture`, `fuzz_capture`) ждут `WARMUP_SETTLED` (1024) тиков — столько же, сколько
модель проигрывает прогрев без поля `warmup`, — чтобы линии лент успели слиться, а руки доехать
(docs/mechanics/belts.md, «Состояние после постройки»). Эталоны 11.10.2026 сняты с ожиданием
600 тиков (модель с прогревом 1024 на них совпадает — числа в docs/model-fidelity.md), эталоны
до 11.10 — с меньшим и не записанным прогревом. Снимок t = k — состояние после k
обновлений игры. Все снимки читаются в `on_tick` в одной и той же фазе тика.

## Факты, снятые с эталонов

- `p` — расстояние **до конца тайла** ленты (по ходу движения) в 1/256: предмет едет, `p` падает на
  скорость ленты за тик (8 / 16 / 24), при переходе на следующий тайл `p` прибавляет 256.
  Упёршиеся в конец предметы стоят на p = 0, 64, 128, 192 (шаг 64).
- Направление манипулятора: `direction` — сторона, **откуда он берёт** (`west` — берёт с запада,
  кладёт на восток). Поднимает с `pickup_position` = центр соседнего тайла в этом направлении,
  кладёт в `drop_position` на 307/256 тайла от центра (x = 2.69921875 для манипулятора в 1.5).
- Манипулятор на ленту кладёт на дальнюю от себя линию; при кладке «в лоб» (вдоль ленты) — на линию 2.
- Из сундука манипулятор берёт из **последнего** непустого слота (из 100 + 100 — из второго).

## Пробы M0.5: предел линии, спящие при разрезе и слиянии

- `lim-*` (генератор — `bench/m05-probes/gen_limit.py`): лента из 205–216 тайлов и источники у границы
  линии в 200 тайлов. Мод в репозитории держит сущности в квадрате ±64 тайла, а лента длиннее 200 тайлов
  туда не помещается, поэтому такие пробы сняты копией мода с `LIMIT = 150`, `CLEAR = 192`,
  `CHUNK_RADIUS = 6` в `scene.lua` (больше ничего не менялось). В `probes/` лежат две из десяти
  (остальные — того же вида, дамп 6–13 МБ каждый; пересъёмка — `gen_limit.py` и `fuzz_capture --batch 1`).
- `sl-rewrite-*`, `sl-merge-*`, `sl-decay-a`: сцены найдены перебором случайных сцен — прогоном модели с
  подменённым правилом (обратный порядок перезаписи спящих при разрезе; обратный порядок и отсутствие
  побудки при слиянии) и отбором сцен, где подмена меняет дамп. Игра совпадает с моделью, подмены
  расходятся (тики — в комментарии у списка проб в `tests/fidelity.rs`). Пробы снимаются по одной
  (`--batch 1`).
- `ao-order-a`, `ao-order-b` (300 и 360 тиков, сняты 500): порядок будильников внутри одной группы линий. Лента из 16
  тайлов, два источника (тайлы 0 и 6, южная сторона), два быстрых стока на тайлах 3 и 9 с кастомными
  векторами (выгрузка в один сундук между ними), в сундуке места ровно на один предмет из пары. После нарезки
  (тик ~182) оба стока спят на пустых отрезках одной цепочки и просыпаются в одном тике от переезда предмета
  через границы линий; кто положит в сундук последнее место, определяет порядок звонков. Игра совпала с
  моделью («порядок обновления отрезков»); подмена «голова → хвост» расходится на тиках 210 и 280. Снимать
  по одной сцене (`--batch 1`).
- `ao3-a`, `ao3-b` (240 и 320 тиков): та же сцена, но с третьей парой (источник на тайле 12, сток на 15 в
  отдельный сундук) — в тиках 115 и 185 в одной группе звонят три будильника. Игра = модель.
- `gr-*`, `gs-*`, `gz-*`, `sy-*`, `gl-*`, `gm-*`, `gn-*` (130–300 тиков): два предмета на земле в тайле захвата
  манипулятора без источника. Источники — два манипулятора с кастомными векторами выгрузки в один тайл (железо и
  медь, чтобы по `held` видеть, что взято); `gr`/`gs`/`gz` — разные расположения пары (диагонали, оси,
  несимметричные расстояния до точки захвата, отрицательные координаты), `sy` — оба предмета положены в один тик
  ждущему манипулятору, `gl`/`gm`/`gn` — второй предмет кладётся в разное время относительно возврата руки
  (цель выбирается один раз). Правило и граница — docs/mechanics/inserters.md, «Манипулятор без цели: земля», п. 5.

## Пробы M0.5: будильники выгрузки и условие «есть место»

Снимать по одной сцене (`fuzz_capture --batch 1` или `scene_capture` с одной сценой): исход части проб
зависит от списка групп, общего на карту. Модель совпала во всех 62.

- `da-line-imm-*` (3), `da-line-def-*` (3), `da-line3-*` (4), 300–800 тиков: два или три манипулятора кладут
  в одну точку ленты (зеркальные векторы `[±1, 1.2]` с соседних тайлов, разные предметы — победителя видно по
  `held` и по ленте). Тупиковая лента из 3–5 тайлов забивается; сток снимает предмет под точкой выгрузки
  (`imm` — звонок сразу) или в конце ленты на другой линии (`def` — отложенный звонок). Буквы в имени — типы
  манипуляторов и порядок постройки. Первым кладёт раньше заснувший.
- `da-chest-*` (4, 300 тиков): три манипулятора кладут в полный сундук, четвёртый забирает по одному.
- `da-lanes-*` (3, 700 тиков): два манипулятора кладут на две полосы одной ленты из общего сундука-источника
  и спорят за последний предмет; порядок — по списку активных групп.
- `da-ground-*` (4, 300 тиков): два манипулятора кладут в одну точку на земле, третий забирает; сна нет.
  Первые выгрузки проходят у обоих (третий забирает предмет сразу); когда ждут оба, кладёт построенный
  позже (в `da-ground-fb` — с тика 151). Предметов на земле в дампе нет: сверяются руки и сундук третьего.
- `da-chain-*` (2, 600 тиков): 3–4 кладущих на разных линиях одной полосы, два звонка выгрузки в одной группе
  в одном тике. Совпали, но правило не различают: подмена порядка линий дамп не меняет.
- `da-lines-*` (9, 300–700 тиков): лента из 4–8 тайлов разных типов (смена типа — граница линии), сток в
  конце, пары кладущих через тайл берут из общего сундука (векторы захвата `[±1, -1]`) и кладут на разные
  линии одной полосы. Два звонка выгрузки в одной группе в одном тике идут в порядке обновления линий;
  обратный порядок меняет дамп во всех девяти.
- `da-mix-a` (500 тиков): то же семейство; в одной группе в одном тике два звонка выгрузки и звонок захвата,
  подмена «сначала звонки захвата» меняет дамп.
- `rm-fg-*`, `rm-fg16-*`, `rm-fg32-*` (10, 480–800 тиков): после снятия первого предмета линии передний зазор
  ровно «скорость + 64» (скорости 8, 16, 32) — спящий кладущий не просыпается. Сдвиг очереди на «скорость»
  дают повороты ниже по течению; `-ex` и `-tu` — лента ниже по течению другой скорости.
- `rm-pos-*`, `rm-pos16-*`, `rm-pos24-*`, `rm-pos32-*` (7, 400–480 тиков): положительный контроль — после
  снятия передний зазор больше границы (79–108, скорости 8, 16, 24, 32), спящий просыпается и кладёт тиком
  позже.
- `rm-sum-*`, `rm-sum16-*` (8): как `rm-fg-*` плюс пустой тайл ленты другого типа сзади — хвостовой зазор
  ровно 64 при пустой линии сзади, манипулятор не кладёт.
- `rm-ctl-*`, `rm-ctl16-*` (4): контроль — хвост не заполнен, манипулятор кладёт тиком позже снятия.

Тики расхождения подменённых вариантов — в комментариях у списка проб в `tests/fidelity.rs`; правила —
docs/mechanics/inserters.md («Порядок, сон и пробуждение») и docs/mechanics/belts.md («Условие „есть место
на линии“»).

## Пробы M0.5 п. 7: рельс и вагон

- Мод принимает в сцене `straight-rail` (рельс 2×2: центр на **нечётных** целых координатах, игра сама
  подгоняет; `direction` `north`/`east`) и `cargo-wagon`/`locomotive` (на рельсе, центр целый; направление
  вагона `north`/`east`/`south`/`west` переводится в orientation). Рельс занимает четыре тайла; вагон тайлов не
  занимает. У вагона можно `items` (содержимое грузового вагона), `at` (вагон ставится в тик `at` прогона,
  `1..ticks`) и `until` (вагон сносится в тик `until`, больше `at`). Эти три поля читает только мод.
- `scene_run` / `scene_run_all` принимают `"status": true`: в запись манипулятора добавляется `"status"`
  (имя из `defines.entity_status`, например `waiting_for_train`, или `null`), а в снимок тика — массив
  `"wagons"` (`pos`, `items`). Без флага дамп прежний; `"ext": true` (теперь и у `scene_run`) работает как
  раньше. Модель и парсер эталона лишних полей не читают.
- `probes/rl-*` — статичные сцены с рельсом (снимаются `scene_capture`; модель рельс знает, вагоны — нет).
  `wagon/rl-leave-ul-<t>.dump.jsonl` — эталоны сцены «сундук → манипулятор → вагон, вагон уезжает в тик t»
  (снимались вручную через `/fd`, сцена с вагоном для модели недопустима; тест
  `train_leaves_while_inserter_holds` воспроизводит их моделью с земли на `Train` в тик t).
